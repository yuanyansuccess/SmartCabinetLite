边缘计算机软件 · 需求卡片与流程设计

文档目的：给边缘计算机软件开发组一份「做什么、怎么算做好」的完整清单，新人读完即可明确职责边界与验收口径。
依据：上位机现行通信代码（CommTypes.h / EdgeService，帧名与参数完全一致）、《出入库边缘机识别流程设计图》V4、边缘机模拟器现行行为。编制：袁燕 · 2026-10-25（同日二轮完善：RTSP 拍板落地、新增 F6/F7/F8 异常流程图与 E21~E32 异常项）。

一、系统定位：边缘计算机在整个系统里的位置

范围声明：柜内工具的视觉识别与图像处理由边缘计算机承担；人脸识别（特征提取、方位检测）部署在上位机侧；数据库、台账、出入库业务判断也都在上位机侧——边缘计算机不碰业务库，只做「通信、识别、控制」三件事并如实上报。

二、边缘计算机要做的三件事（总纲）

① 通信：让上位机随时知道你活着

作为 TCP 客户端主动连接上位机（服务端，端口 9000）；
每 3 秒发一帧 periodic 心跳，携带 8 路摄像头自检状态；
收到请求必须回应：要么回结果、要么回失败，禁止沉默；
断线按退避序列自动重连，恢复后补报缓存事件。

② 识别：如实上报柜内每一格有什么

8 路摄像头（CAM1~CAM8）采集货位画面；
收到 recognize_req 后逐货位检测识别（类别 + 置信度）；
组装全柜实况清单 recognize_ack，字段一律带全；
判定错放 / 未知物 / 缺失 / 置信度不足并给出级别。

③ 控制：真的开锁、真的知道门关没关

通过 TCP 与 IO 板通信；
收到 open_req 后开锁，必须拿到 IO 回执才算成功；
门磁输入点去抖后产生「柜门已关」事件上报，触发识别；
IO 板离线时开锁请求直接拒绝，绝不假装执行。
三条铁律（评审与验收按此三条一票否决）：
1）如实上报——自检不造假、开锁不假成功、识别不用旧帧冒充：任何「假成功」都是最高级事故；
2）必须回应——上位机应答超时 3 秒、最多重发 2 次，沉默等于用户在界面白等 9 秒；
3）断线自愈——断网自己按 1/2/4/8/16/30 秒退避重连，断连期间事件本地缓存，恢复后自动补报且不重复。

通用规则（协议第 3.6 / 5 / 6 章）：应答超时 3 秒、最多重发 2 次（首发 + 2 次重发，request_id 不变）；request_id 配对，同一请求的重复回应只算一次；单帧上限 1MB；链路离线时上位机禁止下发任何请求；断链恢复后上位机对失败请求按原 id 自动补发一次。

五、需求卡片（22 张，按开发组分工）

每张卡回答五个问题：做什么、输入、输出、关键规则、怎么算验收。卡片编号即任务编号，可直接用于排期与评审。

A 组 · 通信与协议（6 张）

A1 · TCP 客户端连接与断线重连

做什么：作为 TCP 客户端主动连接上位机（服务端，端口 9000），断开后自动重连。
输入：上位机 IP、端口（本地配置文件）。
输出：可用的 TCP 链路。
关键规则：退避序列 1/2/4/8/16/30 秒封顶循环；同一时刻只保持一条连接；重连成功后先发一帧 periodic。
异常与边界：连接被拒、超时、网络不可达一律走退避，禁止无间隔狂连刷日志。
验收标准：拔网线恢复后 30 秒内自动重连成功；日志可查每次尝试。

A2 · 周期帧心跳（periodic）

做什么：每 3 秒发送一帧 periodic：运行时长 + 8 路摄像头自检状态。
输入：摄像头自检结果、运行时长。
输出：periodic JSON 帧。
关键规则：间隔 3 秒、帧不能停（15 秒未达上位机即判离线）；自检未启用时 cameras 可为空，帧照发。
异常与边界：发送失败等同断链，立即转入重连流程。
验收标准：上位机每 3 秒收到一条；停发 15 秒后上位机告警离线（与模拟器行为一致）。

A3 · 帧编解码与可靠性

做什么：长度前缀分帧 + JSON 解析，坏帧丢弃并计数。
输入：TCP 字节流。
输出：合法 JSON 帧。
关键规则：单帧上限 1MB；粘包、半包正确拆包；解析失败、超长、未知类型一律丢弃 + 计数 + 日志，不影响后续帧。
验收标准：注入半帧、粘包、超长帧、非法 JSON：不崩溃、不误执行。

A4 · 请求配对与去重（request_id）

做什么：以 request_id 配对请求与回应，同一请求只执行一次。
输入：open_req / recognize_req。
输出：携带原 request_id 的应答。
关键规则：处理前先查在途与已完成表；重复请求回缓存结果或明确拒绝；回应必须带原 request_id。
异常与边界：重复的 open_req 绝不二次开锁（安全红线）。
验收标准：同一 open_req 连发两次，只执行一次开锁。

A5 · 版本应答（version_query / version_ack）

做什么：收到版本查询后回 version_ack，携带软件版本号。
输出：version_ack（version 字段）。
验收标准：上位机能取到版本号并留痕，用于验收与现场排查。

A6 · 断连期间缓存与补报

做什么：断连期间产生的柜门关闭等事件本地缓存，恢复连接后按序补报。
关键规则：缓存带上发生时间、有条数上限防撑爆内存；补报不重复（与实时上报同一去重口径）。
验收标准：断网期间关柜、恢复网络后，上位机能收到补报事件且仅一次。

B 组 · 视频与识别（6 张）

B1 · 多路视频采集（RTSP，已拍板）

做什么：对 8 路网络摄像头（CAM1~CAM8）RTSP 拉流，每路独立会话取流。
关键规则：单路断流按 5/10/30 秒退避自动重连，不影响其他路；码流格式（H.264/H.265）会话协商确认，解码器不支持即置 comm_error 上报。
验收标准：拔掉任一路网线，其余路照常出图；恢复后该路自动回流。

B2 · 解码与抽帧（RTSP）

做什么：RTP 解包 + 解码，识别时取每路「当前帧」。
关键规则：解码队列只保留最新画面——网络抖动积压时强制跳到最新关键帧；识别结果必须反映关柜那一刻的现场，禁止用积压旧帧。
验收标准：人为制造网络抖动，识别用帧仍与现场实际摆放一致。

B3 · 工具检测与分类（模型推理）

做什么：目标检测 + 分类模型，输出目标框、类别、置信度。
输入：视频帧。
输出：货位上工具的 class_id、confidence。
关键规则：模型文件启动时校验，缺失或损坏则自检失败、拒绝识别请求。
验收标准：对在册工具样本识别稳定，置信度可解释。

B4 · 货位结果聚合与告警判定

做什么：检测目标按「货位-摄像头映射」聚合成全柜实况清单。
输出：每货位字段带全：position / tool_id / class_id / confidence / alert_type / alert_level；现行协议以正式需规表 13 为准。
判定规则：有物但类别不符→misplaced；有物认不出→unknown；置信度低于阈值→low_confidence；货位未回报（缺失由上位机判定）。
验收标准：与模拟器内置场景逐一对拍：正常 / 有借有还 / 错放 / 未知物 / 置信度不足 / 缺失，字段口径完全一致。

B5 · 识别请求执行（recognize_req 处理）

做什么：收到识别请求后执行全柜扫描，组装清单回 recognize_ack。
关键规则：去重先行（A4）；单次识别期间再来的请求按忙处理；全程设处理超时兜底——超上限立即回失败帧，禁止沉默。
性能目标（已拍板）：全流程 3 秒内给结果——与上位机应答超时对齐，超时立即回失败帧。
验收标准：正常 3 秒内回包；造超时场景仍能收到失败帧而非无响应。

B6 · 摄像头自检与状态上报

做什么：每路自检状态（ok / offline / low_light / dirty / comm_error）随 periodic 上报，状态变化即时反映在下一帧。
安全红线：自检必须真实——上位机以「任一路非 ok 即禁止开柜」为安全闸门，恒报 ok 等于替现场拆掉闸门。
验收标准：人为遮挡一路，下一帧周期帧即见对应异常状态。

C 组 · IO 控制（4 张）

IO 板硬件尚未到位（2026-10-25 拍板）：本组 4 张卡软件先行——按协议桩开发，联调期用 IO 板模拟器（TCP 接口）代替真实 IO 板（开锁与门磁信号可配置模拟）；真实点位表到位后只改配置与地址，不改架构。

C1 · IO 板连接与自检

做什么：通过 TCP 与 IO 板通信，持续维护连接状态。
关键规则：断线即时感知并记日志；开锁前必查 IO 在线。
验收标准：断开 IO 板网线，边缘机 1 秒内感知并记录。

C2 · 开锁控制（open_req 处理）

做什么：收到开锁请求后驱动 IO 板开锁，回 open_ack（success / message）。
关键规则：写线圈后必须等 IO 回执或状态确认才算成功；失败重试最多 3 次后如实回失败；重复 request_id 拒绝执行。
安全红线：未收到 IO 回执，绝不回报「已开锁」。
验收标准：正常开锁 success=true；拔掉 IO 网线后请求得到明确的失败回应。

C3 · 柜门检测与关柜事件

做什么：门磁输入点判定柜门状态，去抖后产生「柜门已关」事件上报上位机，触发识别。
关键规则：去抖（连续多次采样一致才认定）；断连期间走缓存补报（A6）；同一次关柜只报一次。
当前衔接：上位机现有版本以「我已关柜」按钮顶替该事件，事件帧为交付目标，帧名与字段以协议定稿为准。
验收标准：关柜后上位机能稳定收到一次（且仅一次）关柜事件。

C4 · IO 板状态监测

做什么：IO 板在线状态持续监测，异常随日志与事件反映。
关键规则：IO 离线时开锁类请求快速失败（fail-fast）：立即回明确失败原因，不假装执行、不让上位机干等超时。
验收标准：IO 离线期间收到 open_req，立即收到失败回应而非超时。

D 组 · 系统与运维（6 张）

D1 · 启动自检

做什么：上电自启后逐项自检：配置、网络、IO 板、8 路摄像头、识别模型、连接上位机。
关键规则：自检结果决定能力开关——IO 失败=禁止开锁；部分摄像头失败=对应路 offline 上报；模型失败=拒绝识别；任何一项失败不阻断其余模块启动。
验收标准：逐项拔硬件冷启动，自检结果与实际一致。

D2 · 配置管理

做什么：本地配置文件管理：上位机 IP / 端口、IO 板地址、货位-摄像头映射、识别阈值、日志目录。
关键规则：货位-摄像头映射必须与上位机台账一致（全柜覆盖识别的基础）；口令、密钥不明文落盘。
验收标准：修改映射后识别范围随之变化，无需改代码。

D3 · 日志

做什么：通信日志（关键帧收发）、识别日志（每次清单与耗时）、异常日志；本地滚动清理。
关键规则：时间戳与 NTP 对齐，可与上位机日志对账；磁盘写满时滚动覆盖，业务不受影响。
验收标准：任一次识别可凭日志还原「请求、采集、回应」全过程。

D4 · 守护与自启（Linux systemd）

做什么：systemd 服务托管：崩溃自动拉起、开机自启、断电恢复后自动回到工作状态。
关键规则：Restart=always；启动失败有明确日志可查。
验收标准：kill -9 后 5 秒内自动恢复并重连上位机。

D5 · 时间同步（NTP）

做什么：与内网 NTP 源校时。
关键规则：识别时间、日志时间与上位机可对齐——现场对账、排查纠纷的依据。
验收标准：与上位机时间偏差在 1 秒内。

D6 · 交付与部署

做什么：Linux 环境整包交付：程序 + 配置 + 模型 + 视频卡驱动 + 部署文档；版本号接入 version_ack。
关键规则：交付前在目标硬件上完成全流程联调（连接、开锁、识别、断线自愈）。
验收标准：全新设备按文档 30 分钟内部署完成并通过自检。

F3 · 识别业务流程（recognize_req 处理）

超时兜底红线：识别全程设处理上限（建议与上位机口径对齐：3 秒内必须给结果），超过上限立即回失败帧——「沉默不回应」会让上位机按 3 秒 × 3 次重发白等 9 秒，用户界面长时间停留在「正在核对柜内工具」。

F4 · 开锁控制流程（open_req 处理）

开锁红线：未收到 IO 板回执，绝不回报「已开锁」。开锁假成功 = 用户以为柜门开了实际没开，或实际开了系统却不知道，属于最高级事故。

F5 · 柜门关闭事件流程（触发识别的源头）

衔接说明：上位机现有版本以「我已关柜」按钮顶替本事件；事件帧（帧名、字段）以协议定稿为准，上位机侧已按事件入口解耦，切换时上位机页面无需改动。

F6 · RTSP 视频链路流程（每路独立，已拍板网络摄像头）

RTSP 专属异常（视频链路不通不等于整机故障）：拉流失败按 5/10/30 秒退避重连该路；解码器不支持码流格式（如 H.265）置 comm_error 上报人工排查；网络抖动导致解码队列积压时强制跳最新关键帧——宁可丢旧帧，绝不用积压旧帧识别；黑屏 / 花屏 / 冻结帧由画面异常监测捕捉置 dirty。单路故障只影响该路货位，其余路照常。

F7 · 识别时机与画面质量闸门（拍空柜、边界误判的防线）

识别前先过质量闸门：门磁防御式复核（柜门没关收到识别请求，回失败而不是照拍——防止拍空柜、拍到人手）；关柜后画面可能还在晃（门弹跳、工具没放稳、灯光突变），稳定期 1~2 秒 + 连续多帧一致才采信；单货位检测到多个目标（工具叠放）取最高置信度并如实标注。

F8 · 上电恢复与开锁幂等保护（崩溃 / 断电重启后防二次开锁）

高危场景（必须实现）：边缘机在「写完开锁线圈、还没回 open_ack」的瞬间崩溃——上位机收不到回应，链路恢复后会按原 request_id 补发。重启后的边缘机内存登记表已清空，若把这条补发请求当新请求重新执行，就是二次开锁。防线：开锁类请求执行前先落盘登记，重启后读到未完成的开锁请求，必须先查 IO 锁状态——已开只补回执；状态未知拒绝重发、报人工确认。

八、异常场景清单（边缘机视角，32 项）

#类别场景边缘机正确行为禁止的做法
E01网络上位机未开机 / 端口未监听按退避序列重连；本地自检与日志照常运行无间隔狂连，日志刷屏
E02网络运行中网络闪断停周期帧，退避重连；恢复后补报缓存事件以为还在线继续发帧
E03协议坏帧 / 半帧 / 粘包分帧容错，坏帧丢弃并计数解析崩溃或误执行
E04协议收到未知 type 帧丢弃 + 计数 + 日志，继续处理后续帧整机重启或丢弃所有后续帧
E05协议同一 request_id 重复请求去重：回缓存结果或明确拒绝对 open_req 二次开锁（安全事故）
E06业务识别进行中又来识别请求忙判定：明确回应忙或排队，一次只跑一套识别并发跑两套识别互相污染结果
E07业务识别处理卡死处理超时兜底：立即回失败帧沉默不回应，上位机白等 9 秒
E08摄像头单路断流该路置 offline，对应货位不回报（清单缺项，由上机位判识别核对异常）用上一帧冒充当前画面（假识别）
E09摄像头画面脏污 / 遮挡 / 低照度置 dirty / low_light 并上报，识别结果如实标注恒报 ok——等于替现场拆掉开柜安全闸门
E10摄像头全部摄像头离线拒绝识别请求并回明确失败回空清单——上位机会误判「整柜空」
E11IOIO 板离线开锁请求快速失败：立即回 success=false 与原因假装成功或让请求干等到超时
E12IO开锁无回执重试最多 3 次，仍失败如实回报未拿回执却回「已开锁」（假开锁）
E13IO门磁信号抖动去抖：连续多次采样一致才认定关柜抖动当多次关柜，重复触发识别
E14系统程序崩溃systemd 自动拉起，重新自检并重连无守护进程，柜子变砖
E15系统断电恢复开机自启：自检、重连、补报缓存事件需要人工上机操作才能恢复
E16系统磁盘写满 / 日志失败日志滚动清理，业务不受影响日志撑爆磁盘拖垮整机
E17系统模型文件缺失 / 损坏自检失败，拒绝识别请求并告警加载失败还硬跑出垃圾结果
E18系统时间不同步NTP 校时，保证与上位机日志可对账日志时间错乱，现场无法排查
E19安全第二台客户端抢连与上位机约定单连接策略：拒绝新连接或踢旧（需定稿）两个上位机同时控一台柜
E20安全超长帧 / 恶意帧1MB 上限 + 长度校验，超限丢弃计数无上限解析，内存被撑爆
E21RTSP拉流失败（认证错 / IP 错 / 摄像头重启）该路按 5/10/30 秒退避重连，自检置 offline（见 F6）无间隔狂连，或谎报正常
E22RTSP码流格式不支持（如 H.265 解码器缺失）会话协商阶段发现，置 comm_error 上报人工排查装看不见继续解出垃圾帧
E23RTSP网络抖动导致解码队列积压强制跳到最新关键帧，只用当前帧识别（见 F6）用积压旧帧识别——结果滞后于现场
E24RTSP花屏 / 黑屏 / 冻结帧画面异常监测捕捉，置 dirty 并随周期帧上报当正常帧送识别
E25重启开锁后回执前崩溃，上位机补发原请求开锁请求先落盘登记；重启后先查 IO 锁状态——已开只补回执，未知拒绝重发报人工（见 F8）不查状态重新执行——二次开锁事故
E26业务柜门未关时收到识别请求门磁防御式复核，回失败「柜门未关」（见 F7）照拍不误——拍空柜、拍到人手
E27业务关柜瞬间画面晃动 / 工具未放稳稳定期延时 1~2 秒再采，连续多帧一致才采信（见 F7）门一关立刻拍，边界误判
E28业务瞬时光照突变（开灯 / 补光灯闪）多帧投票，不一致再等一轮重采（见 F7）单帧定生死
E29业务单货位多目标 / 工具叠放取最高置信度目标，并按告警规则如实标注（见 F7）随机取一个或漏报
E30系统上位机异常狂发请求（请求风暴）限流：超阈值直接拒绝并计数告警来者不拒把自己拖死
E31系统NTP 校时引起时钟回拨计时（超时 / 退避 / 去抖）一律用单调时钟，墙钟只用于日志用墙钟计时——校时后超时全乱
E32部署两台柜网线插错（边缘机接错上位机）上报柜号 / 序列号供上位机绑定校验（帧字段待协议定稿）无绑定校验——B 柜被 A 柜控制

十、确认与待确认问题清单

已拍板（2026-10-25）：
✔ 视频接入形态 = 网络摄像头 RTSP 拉流（对应卡 B1/B2、流程图 F6）；
✔ 识别耗时上限 = 3 秒内给结果，超时立即回失败帧（对应卡 B5）；
✔ IO 板硬件暂未到位——软件按协议桩先行，联调用 IO 板模拟器（TCP 接口），点位表到位后只改配置不改架构（对应 C 组）。
仍待确认：
1）IO 板点位表：开锁点、门磁输入点等点位，回执方式（读回状态还是 IO 主动上报）——硬件到位后定。
2）关柜事件帧：帧名与字段定稿（当前上位机按钮顶替路径保留，事件到达即无缝切换）。
3）货位-摄像头映射：边缘机本地配置，还是上位机下发 + 本地缓存？建议后者，保证与台账一致。
4）多连接策略：只允许一台上位机连接时，第二连接拒绝还是踢旧？
5）模型与阈值：检测模型选型（本地推理框架）、置信度阈值与 low_confidence 门槛值。
6）补报事件范围：断连补报目前只含关柜事件，是否包含摄像头异常历史。
7）柜号绑定校验：边缘机上报柜号 / 序列号、上位机校验绑定，防两台柜网线插错（见 E32）——帧字段待协议定稿。
