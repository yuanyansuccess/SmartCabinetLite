边缘计算机软件 · UML 设计图（需求驱动）

设计来源：边缘计算机软件需求与流程设计.html 的 22 张需求卡 + 协议对齐表 + 8 张流程 + 3 张时序 + 32 项异常。
实现目标语言：Python（本文件仅交付设计，不含代码）。本图与需求卡的对应关系：A 组通信 6 卡 → TCP 模块与 Controllers；B 组识别 6 卡 → 识别模块；C 组 IO 4 卡 → IO 控制模块；D 组系统 6 卡 → 系统服务；F1~F8 流程 → 活动图；E01~E32 异常 → 各类图的方法与红线。
分层铁律（与袁总要求一致）：数据层 ← TCP 模块（三线程）→ Controllers（小控制层）→ 大控制层/抗冲落层（EdgeControl）整体调度；数据层与控制层通过接口解耦（依赖注入），保证后期易维护。

一、总体分层架构图

线程协同模型：① 重连线程 监测链路、断线按 1/2/4/8/16/30 秒退避重连，重连成功后经 TcpControlLayer 通知大控制层补报缓存；② 接收线程 收字节 → 在 TcpControlLayer 内部完成「分帧+解码+解析」直接产出带类型信号（open_req / recognize_req / version_query / ack），通过注入的 SignalSink 抽象接口上抛（TCP 模块不依赖任何 Controller）；③ 心跳线程 每 3 秒经 TcpControlLayer 发 periodic。三个线程共享 TcpControlLayer 持有的 socket，发送加锁、接收入队，由 TcpControlLayer 统一协同。大控制层 EdgeControl 实现 SignalSink 接口消费信号做跨模块编排、故障隔离与断连缓存补报。

二、类图（覆盖功能性方法）

2.1 TCP 模块类图：门面 + 三内部线程 + SignalSink 解耦出口（覆盖 A1~A6 通信需求卡）

需求卡覆盖对照（每张卡落到具体的类与方法）：
A1 连接与断线重连 → TcpReconnectThread：退避 1/2/4/8/16/30 秒封顶循环；被拒/超时/不可达一律走退避；同一时刻仅一条连接（门面 _sock 单一持有）；重连成功 _on_connected() 通知门面并先发 version。
A2 周期心跳 → TcpHeartbeatThread：每 3 秒 _build_periodic()（运行时长 + 8 路摄像头自检）；发送经门面 send_frame() 加锁；发送失败等同断线 → 立即转重连流程。
A3 帧解析与可靠性 → TcpRecvThread 内聚（不单独成类）：_split_frames() 长度前缀分帧（粘包/半包正确拆）、单帧上限 1MB、_decode_and_parse() 坏帧丢弃 + 计数 + 日志，不影响后续帧。
A4 请求配对与去重 → Signal.request_id 全链路透传：接收线程回应必须带原 request_id；去重判定与"重复 open_req 不二次开锁"由 EdgeControl + PendingRequestStore 执行（2.2/2.3），TCP 层只负责透传、不吞不改。
A5 版本应答 → VersionQuerySignal 经 SignalSink 上抛，EdgeControl 路由到 VersionController 回 version_ack；断线重连成功后由重连线程主动补发 version（与 A1 衔接）。
A6 断连缓存与补报 → 门面 _notify_state_change() 产出 LinkStateSignal（断开/恢复各一次）→ EdgeControl on_link_down() 事件入缓存、on_link_up() 按序补报不重复（缓存本体 EventCache 见 2.3）。
关联关系读法（图例）：实心菱形 = 组合（门面持有三线程、同生命周期，外部只看得见 TcpControlLayer 一个类）；虚线箭头 = 依赖；深蓝依赖边 = 线程对门面的回调（重连成功通知 / 发送失败转重连）；灰框 = 抽象接口与数据载体（TCP 不认识任何 Controller）。
解耦出口（依赖倒置）：TCP 模块只依赖 SignalSink 抽象接口；大控制层 EdgeControl 实现该接口，初始化时经 set_signal_sink() 把自己注入门面。数据流向：TcpRecvThread 内聚解析 → SignalSink.on_signal(signal) → EdgeControl.route_signal() → 具体 Controller。二者仅通过 Signal 数据对象 + SignalSink 接口耦合，可独立测试、独立替换。
两条向上回调边：① 重连线程 _on_connected() → 门面（先发 version）；② 心跳线程发送失败 → 门面（立即转重连）。三线程与门面的全部交互都经门面中转，线程之间互不直连。

2.1.1 三线程怎么配合（新手白话版）

把 TcpControlLayer 想成一部电话总机，三个线程是总机里三位各管一摊的员工。电话线（socket）只有一根，归总机保管，谁要用谁先拿锁：
角色管什么怎么干（白话）
接收线程听话一直贴着电话听。听到一串字节就按长度切成一条条完整消息，翻译成 Signal，投进 SignalSink 这个"信箱"。听不清的（坏帧）整条扔掉并记一笔，绝不耽误听下一条。
心跳线程报平安定一个 3 秒的闹钟，每响一次就对电话说一句"我还活着，8 路摄像头状态如下"。哪天发现话说不出去（发送失败），立刻报告总机：线路断了。
重连线程修线路线路一断就接手：通知总机停心跳、缓存事件，然后按 1/2/4/8/16/30 秒越来越长的间隔重拨，直到拨通。拨通后第一件事是自报版本号，再通知总机"线路恢复了"，大控制层把断线期间攒下的事按序补报上去、不重复。
三条配合规矩（记住这三条就懂了）：
① 线程之间从不直接说话——接收线程收完帧、心跳线程发送失败、重连线程拨通线路，全部只报告总机（TcpControlLayer），由总机统一决定下一步。好处：出问题只查一个地方，不会三个线程互相甩锅。
② 发送要拿锁，一人一句——三个线程都可能要发帧，谁拿到 _lock 谁先发，避免两个人的话在电话线里搅成一团。
③ 收和办分开——接收线程只负责"收下来、翻译好、投信箱"，至于这条请求该不该开锁、要不要识别，它一概不管，由大控制层 EdgeControl 决定。所以 TCP 模块可以单独测试、单独更换，不牵连业务。
新手最容易被问倒的两个点：
① "断线是谁先发现的？"——通常是心跳线程：它每 3 秒要说话，最先发现"说不出去了"。接收线程也能发现（连接被挂断、recv 返回 0），两条路都汇到总机，由总机统一宣告断线，不会重复宣告。
② "重连期间收到的请求怎么办？"——收不到。线路断了就没有"收"这件事，上位机那边的请求靠它自己的 3 秒超时×重发兜底；我们这边断线期间发生的事（如关柜事件）先进 EventCache 落盘，线路恢复后补报，一件不丢、一件不重。

2.1.2 异常帧处理清单（接收线程视角）

场景：上位机经网络发来 recognize_req 要求读柜内清单，请求在网络上传，什么都不足为奇——两条粘一起、一条断两截、缺字段、重复发、到的顺序乱。接收线程对每一种都必须有明确动作：要么完整处理，要么整帧丢弃，绝不"处理一半"。下面这张表就是异常帧的完整处置口径（实现时落在 _split_frames() 与 _decode_and_parse() 两个方法里）。
异常情况长什么样处理动作
粘包两条帧挤在一次接收里到达按长度前缀切开，两条各自完整走流程，互不影响。
半包一条帧只到了前一半（网络分片）前半截留在缓冲区等下一次接收补齐，不解析、不上抛、不计数（这不是坏帧，是正常现象）。
超长帧单帧超过 1MB 上限整帧丢弃 + 坏帧计数 +1 + 日志；判定为异常数据，不再继续读这条帧。
长度头非法长度=0、负数或明显离谱，找不到帧边界丢弃 + 计数 + 日志，清空缓冲区重新同步。原则：宁可整段丢，不可错位解析——错位会把后面的好帧也全部切坏。
内容解不开不是合法 JSON，或编码损坏整帧丢弃 + 计数 + 日志，不影响后续帧。
缺 request_id请求里没有配对编号丢弃 + 日志，不回应——没有编号就无法配对应答。上位机 3 秒收不到应答会自动重发，靠这个兜底。
缺其他必填字段recognize_req 缺 items、open_req 缺货位号等丢弃 + 计数 + 日志；能拿到 request_id 的，回一帧失败应答让对方别干等。
未知帧类型type 不在协议帧表里忽略 + 计数 + 日志，不断连不报错。这是前向兼容：新版上位机发的帧，老版边缘机不认识也不崩。
重复 request_id上位机超时重发，同一编号来两次TCP 层照常上抛、不吞不改；去重判定由大控制层（PendingRequestStore）做。TCP 层没有在途记录，不替业务做决定，避免把合法的第二次请求误吞。
忙时又来识别请求上一轮识别还没结束，新的 recognize_req 又到了TCP 层照常上抛；业务层回 busy 帧——必须回应，不能沉默（沉默=对方白等 9 秒）。
断线残帧连接断开瞬间，缓冲区里还剩半条帧断开即清空缓冲区，残帧直接扔。新连接不带任何旧数据。
旧连接的帧已判离线、或已换新连接后，旧连接的帧才到丢弃 + 日志——只认当前 socket 的数据，杜绝两台柜/新旧会话串台。
应答配不上对收到的 ack 在在途记录里找不到对应编号丢弃 + 日志（可能是对方对已超时请求的迟到应答）。
对端关闭recv 返回 0 字节这不是坏帧，是对方正常挂断 → 走断线流程，交给重连线程。
异常帧三条处理原则（表格里所有动作都从这三条推出来）：
1）丢弃不连坐：坏帧只扔这一帧，缓冲区对齐后立刻继续收下一帧，不重连、不重启、不连累后面的好帧。
2）丢弃必留痕：每次丢弃做三件事——坏帧计数 +1、写日志（带丢弃原因和原始长度）、把缓冲区恢复到可解析状态。联调时看一眼计数就知道线路质量好坏。
3）能回应必回应，不能回应靠超时：异常帧里还有 request_id 的，回一帧失败应答；连 request_id 都没有的只能丢弃，由上位机的 3 秒超时×重发机制兜底。全程不存在"默默吞掉且对方不知道"的情况。

五、面向 Python 实现的设计要点

安全红线（来自三条铁律与 E 系列异常，必须在类方法中落地）：
1）如实上报：开锁 success=true 唯一前提=拿到 IO 回执；识别禁止用旧帧（B2 积压跳最新关键帧）；摄像头自检真实（B6）。
2）必须回应：识别全程 3 秒超时兜底立即回失败帧（F3/F7）；开锁无回执重试最多 3 次后如实失败（C2）。
3）断线自愈：退避重连 + 断连事件缓存 + 恢复补报不重复（A6）；重发/补发靠 request_id 去重（A4）。
4）幂等：open_req 执行前先落盘登记（PendingRequestStore），崩溃重启后先查 IO 锁状态——已开只补回执，未知拒绝重发（F8/E25）。
松耦合落地建议（Python）：数据层四个 Store 全部以 抽象基类/Protocol 定义接口，由 EdgeControl 通过构造函数注入具体实现；TCP 模块、Controllers、IO、识别模块之间只依赖接口与信号对象（Signal dataclass），不互相持有具体类。这样后期替换 Modbus 模拟器、换识别框架、换存储后端都不动控制层。线程用 threading.Thread + queue.Queue + threading.Lock 实现，TcpControlLayer 持有 socket 与锁，三个线程通过 Queue 把"已解码信号 / 链路状态变化 / 待发帧"交给大控制层与心跳线程，避免共享状态竞态。
